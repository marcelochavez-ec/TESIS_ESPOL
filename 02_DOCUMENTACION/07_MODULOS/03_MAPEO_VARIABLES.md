# MAPEO DE VARIABLES ANTES DE POSTGRESQL

1. **Objetivo.** Determinar el tipo SQL de cada variable antes de almacenarla. El mapeo independiente solo genera metadatos; la recarga autorizada utiliza esos mismos tipos para almacenar las seis fuentes. La recarga aplica después el modelo relacional documentado en 07_MODELO_ENTIDAD_RELACION.md.
2. **Archivos.** `03_PROCESOS_ETL/01_ETL_FUENTES.py` coordina el catálogo; `02_MAPEO_POSTGRESQL.py` centraliza la lógica; `03_PROCESOS_ETL/05_PRUEBAS/01_PRUEBAS_MAPEO.py` contiene pruebas; `05_CONFIGURACIONES/01_PROYECTO.json` declara archivos, rutas, aliases y margen.
3. **Flujo.** Se verifican los ocho hashes de datos/diccionarios; se recupera cada objeto RDS; se recorre cada columna completa; se clasifica su tipo y se valida una copia; se adjunta la etiqueta; se generan catálogo, resumen y propuesta SQL. Solo se escriben metadatos una vez terminado el mapeo de todas las fuentes.
4. **Entradas.** Seis RDS y dos diccionarios declarados en el manifiesto; margen VARCHAR de 10 caracteres por defecto; JSON opcional de declaraciones por tabla/variable mediante --declaraciones. El parámetro --margen-varchar permite cambiar el margen de manera explícita. --salida cambia únicamente el directorio de metadatos.
5. **Salidas.** `02_DOCUMENTACION/08_MAPEO_ENDI/01_MAPEO_VARIABLES.csv` es el único catálogo completo: variable, tipo_origen, tipo_valores, tipo_sql, criterio, nulos, longitud_observada, longitud_declarada, tabla, archivo, objeto, variable_diccionario, etiqueta y registros. El resumen JSON contiene conteos; el SQL contiene exclusivamente tipos de columnas.
6. **Fuentes.** Las tablas son endi.f1_hogar, endi.f1_personas, endi.f2_mef, endi.f2_lactancia, endi.f2_salud_ninez y endi.f3_desarrollo_inf, en research_lab. El generador de catálogo no las crea; el coordinador de recarga sí las sustituye. La guía local es 02_GUIA_BASE_DATOS_ENDI_R2.PDF, revisada completa para este alcance; no se interpretaron todos los indicadores del documento metodológico.
7. **Reglas de tipos.** Un texto de longitud máxima 20 pasa a VARCHAR(30); se cuentan caracteres Unicode, no bytes. Los enteros usan SMALLINT/INTEGER/BIGINT según rango; fuera de BIGINT se usa NUMERIC exacto. Reales originales se conservan como DOUBLE PRECISION aunque sus valores observados sean enteros. Decimal pasa a NUMERIC sin convertirlo a float. Los lógicos reales se distinguen de códigos 0/1.
8. **Fechas.** date pasa a DATE; datetime conserva TIMESTAMP y su zona. Una declaración DATE admite formato explícito y rechaza fechas inválidas o la pérdida de hora/zona. No se adivinan fechas en textos ni se combinan año/mes/día. Los componentes ENDI y códigos 99/9999 permanecen como se recibieron; actualmente las fuentes no contienen columnas de fecha completa.
9. **UI.** No aplica. El comando 01 permite solo mapeo y escritura de metadatos; no tiene una opción de carga ni de creación de constraints.
10. **Funciones.** leer_fuente(ruta, opciones) devuelve todas las hojas/objetos tabulares de RDS/RData, XLS/XLSX, CSV/TSV o Parquet; Parquet necesita su motor opcional y otros formatos se rechazan explícitamente. CSV sin esquema se conserva como texto. mapear_dataframe(df, declaraciones, margen) devuelve copia normalizada, tipos SQLAlchemy y metadatos, sin modificar el original ni abrir conexiones.
11. **SQL y almacenamiento.** definir_tabla() construye columnas; generar_mapeo_endi() compila CREATE TABLE como artefacto de revisión. almacenamiento_postgresql() mapea antes de crear/copiar una tabla nueva y rechaza tablas existentes. La ruta por lote recargar_fuentes_postgresql() mapea todas las fuentes antes de abrir la transacción y recargar_tablas() sustituye las seis tablas mediante DROP RESTRICT, CREATE y COPY, verificando filas, tipos y nulos antes del commit. Esta última ruta sí fue ensayada en PostgreSQL real; se documenta en 06_RECARGA_POSTGRESQL.md.
12. **Dependencias.** pandas, NumPy, pyreadr, openpyxl, xlrd, SQLAlchemy y Psycopg 3. Se conservaron los métodos exploratorio, lectura_diccionario y buscar_variable; la carga automática y la conversión de prov pasando por entero se retiraron porque cambiaban o reemplazaban datos fuera del mapeo solicitado. La conexión usa URL.create y secretos externos.
13. **Validaciones.** Columnas únicas; nombres SQL de hasta 63 bytes; cobertura de todas las fuentes; fechas válidas; rango entero; capacidad VARCHAR; columnas ambiguas declaradas explícitamente; preservación de nulos y filas; rechazo de NUL y de precisión temporal que PostgreSQL no representa. No se están validando todavía relaciones entre tablas.
14. **Pruebas.** La suite verifica 37 casos de tipos, límites, fechas, códigos, decimales, formatos y conservación del original. Una entrada inválida se rechaza antes de abrir una transacción. Se compara también el catálogo completo en dos ejecuciones y entre Windows/Linux, según el informe 03_REPRODUCIBILIDAD.json.
15. **Riesgos y rendimiento.** Se recorre cada columna completa para no dimensionar VARCHAR con una muestra insuficiente. El generador de catálogo procesa una fuente y su copia a la vez; la recarga conserva las seis fuentes normalizadas hasta terminar la transacción. Una futura tanda con textos más largos deberá remapearse; no se amplían tablas existentes silenciosamente. Un tipo object totalmente nulo y sin declaración falla, en vez de inventar su significado.
16. **Cambios.** Se mapearon las 1.423 variables y se añadieron tipos explícitos a la ruta de almacenamiento. Cinco diferencias literales de etiquetas de desarrollo infantil se resuelven mediante aliases explícitos del manifiesto: relacion_cuidadora→relacion_cuidador, fexp_di→fexp y f3_s0_1b_anio/mes/dia→f3_s0_anio/mes/dia. Se conservan los nombres originales en los datos y se indica la variable del diccionario usada; no se aplican reemplazos aproximados.
17. **Integración posterior al mapeo.** La instrucción actual autoriza PK/FK/UNIQUE/CHECK y sustituye el aplazamiento anterior. La recarga aplica 05_MODELO_RELACIONAL.py después de copiar las seis fuentes y antes del commit, sin filtrar registros. La generación independiente del catálogo sigue sin ejecutar DDL. Las pruebas de integración verifican repetición, fechas, tipos, nulos y rollback; el método de almacenamiento individual no tiene una prueba de integración independiente.
